# Dank Lookup v0.4.8: mode routing and source quality

This document is a handoff for opencode. Do not implement immediately unless the
user explicitly switches to build mode.

v0.4.7 made `han`, `yue`, and `ja` coexist locally. The next issue is not
"can the backend find a result", but:

```text
when several monolingual CJK sources match the same selected word,
which mode should be shown first, and which modes should merely be available?
```

The goal is to make real reading behavior predictable without overfitting to
aggressive language guessing.

## Current local state

Current config path:

```text
~/.config/dank-lookup/config.json
```

Current enabled modes:

| Mode | Label | default_for | Source |
|------|-------|-------------|--------|
| `han` | 漢語 | `cjk` | 萌典重編國語辭典 |
| `yue` | 粵語 | `cjk` | words.hk 粵語詞典 |
| `ja` | 日語 | `kana`, `cjk` | reader.dict JA |
| `en-en` | 英英 | `latin`, `mixed` | GCIDE, WordNet |

Current CJK behavior:

- CJK-only query can match `han`, `yue`, and `ja`.
- `available_modes` includes only modes with an exact-result body.
- Default mode is selected by config order among matching `default_for`
  candidates.
- With current config order, common CJK words such as `合格`, `字典`, `春` default
  to `han`, while `yue` and `ja` may remain available as switchable tabs.
- Kana queries such as `日本語` default to `ja`.

This is acceptable as a baseline. v0.4.8 should refine and document it rather
than replacing it with brittle hardcoded language guesses.

## Problem

Chinese, Cantonese, and Japanese share Han characters. A single selected word
can be valid in multiple languages:

```text
合格
春
字典
藝術
臺灣
```

That creates three risks:

1. A Japanese dictionary can match a Han-character word that the user is reading
   in Chinese prose.
2. A Cantonese dictionary can match a general Chinese word, but may not be the
   desired first answer.
3. Over-aggressive auto-detection can hide useful alternate modes.

The UI already supports manual switching, so the backend should prefer
conservative routing:

```text
show all exact modes, pick a predictable default, do not suppress useful tabs
```

## Design principles

### 1. Exact result first

A mode should enter `available_modes` only when it has an exact result body for
the query.

This preserves the v0.4.3 quality rule:

- exact entries belong in the main body
- fuzzy / related entries must not pretend to be the primary definition

### 2. Config order is the primary tie-breaker

When multiple CJK modes exact-match the same query, choose the default from
config order among modes whose `default_for` contains the query class.

For the current local config:

```text
han -> yue -> ja -> en-en
```

So a plain CJK query that matches all three should default to `han`.

This is intentional: for unknown Han-character text, Traditional Chinese /
Mandarin is the safest first pane in this setup.

### 3. Kana strongly promotes `ja`

If the query contains kana, classify as `kana`, and `ja` should be the default
when it has an exact result.

Examples:

```text
日本語 -> ja
かな   -> ja if exact result exists, otherwise mock/no exact state
```

### 4. Cantonese markers may promote `yue`, but must not suppress `han`

Future optional behavior:

If the query contains strong Cantonese-only markers, `yue` may become default.
Examples of possible markers:

```text
嘅, 唔, 咗, 佢, 哋, 冇, 喺, 嗰, 啲, 咁
```

However:

- this is a promotion rule, not a hiding rule
- `han` should remain available when it has an exact result
- the marker list must be config-driven or easy to disable

Do not hardcode a large Cantonese classifier in v0.4.8.

### 5. Japanese Han-character promotion should stay conservative

Do not make `ja` default solely because `reader.dict JA` has an exact match for a
Han-character query.

Acceptable promotion signals:

- query contains kana
- query includes Japanese-specific orthography or punctuation in a future
  classifier
- user manually switches to `ja`
- future user preference: "prefer ja for CJK in current app / profile"

Non-goal for v0.4.8:

- automatic full Japanese sentence detection
- app-specific routing
- OCR or segmentation

## Proposed routing policy

### Classification

Keep the existing coarse classes:

```text
kana
cjk
latin
mixed
```

Do not add heavy natural-language detection in v0.4.8.

### Candidate collection

For each enabled mode:

1. Check whether at least one source matches the query class.
2. Query configured sources.
3. Keep exact entries for the mode body.
4. Add the mode to `available_modes` only if the exact body is non-empty.
5. Keep related/fuzzy entries out of the main body.

### Default selection

Default selection should follow this order:

1. If query class is `kana` and `ja` has exact results, default to `ja`.
2. If optional Cantonese marker promotion is enabled and `yue` has exact
   results, default to `yue`.
3. Otherwise, among `available_modes`, pick the first mode in config order whose
   `default_for` contains the query class.
4. If none match, pick the first `available_modes` item.

For current config, expected defaults:

| Query | Expected default | Expected available modes |
|-------|------------------|--------------------------|
| `合格` | `han` | `han`, `yue`, `ja` if all exact-match |
| `字典` | `han` | `han`, `yue`, `ja` if all exact-match |
| `春` | `han` | `han`, `yue`, `ja` if all exact-match |
| `俳句` | `ja` or `han` depending exact candidates; verify before locking | at least `ja` |
| `日本語` | `ja` | `ja` |
| `藝術` | `han` | `han`; `yue` only if words.hk exact result exists |
| `臺灣` | `han` | `han`; `han-en` absent in current config |
| `adherence` | `en-en` | `en-en` |

Note: `俳句` is a useful edge case because it is a Japanese cultural term written
in Han characters. Do not hardcode it; verify actual mode availability first,
then decide if a fixture should assert default mode or only assert `ja`
availability.

## Source quality policy

### 萌典重編國語辭典 (`han`)

Use as the primary Traditional Chinese / Mandarin monolingual source.

Quality rules:

- exact result goes into main body
- keep readings and definitions
- avoid treating unrelated fuzzy hits as main body
- suitable first answer for generic CJK text

### words.hk 粵語詞典 (`yue`)

Use as Cantonese monolingual source.

Quality rules:

- exact result goes into `yue`
- keep Jyutping
- keep Cantonese definition and examples before English glosses
- English lines are secondary, not the main point
- do not publish converted data unless redistribution permission is confirmed

### reader.dict JA (`ja`)

Use as Japanese monolingual source.

Quality rules:

- kana queries should naturally route to `ja`
- Han-character queries may expose `ja` as an alternate tab
- do not allow `reader.dict JA` to override `han` for generic CJK solely because
  it has an exact Han-character entry
- prefer no-etymology variant for popup readability

### GCIDE / WordNet (`en-en`)

Keep existing v0.4.3 rule:

- exact entries in main body
- fuzzy entries in `related_by_mode`
- GCIDE and WordNet both allowed as exact sources

Do not overload the core four baseline fixtures. Add a new optional fixture set
for real reading routing:

```text
tests/fixtures-reading-routing/

  ja-nihongo.json

  en-adherence.json
```

Run with:

```bash
python3 ~/.local/lib/dank-lookup/tests/run_backend_fixtures.py \
  ~/.local/lib/dank-lookup/tests/fixtures-reading-routing
```

These fixtures should assert:

- `backend == "sdcv"` for known deployed sources
- `default_mode` for stable cases
- `available_modes_contains` for alternate modes
- source subtitle contains expected dictionary names
- body contains short, stable substrings

Avoid over-asserting long definitions. Dictionary bodies can change after source
conversion cleanup.

## Acceptance

Implementation is acceptable when:

- Existing core fixtures remain `4/4 passed`.
- Existing ja/yue fixtures remain `6/6 passed`.
- New reading-routing fixtures pass.
- Generic CJK words still default to `han` under current config order.
- Kana-containing queries default to `ja` when exact results exist.
- `yue` remains available for exact Cantonese entries and can be manually
  selected.
- No network request is introduced.
- No dictionary data is added to repo.
- No QML layout change is required for this step.

## Non-goals

- Big Bang segmentation.
- OCR lookup.
- Network translation.
- LLM explanation.
- Publishing dictionary data.
- App-specific language profiles.
- Full language identification for Chinese/Japanese/Korean text.

## Open questions

1. Should Cantonese marker promotion be implemented in v0.4.8, or left as a
   later config option?
2. Should `俳句` default to `ja` because it is culturally Japanese, or should
   default selection stay purely config-driven?
3. Should `ja` be removed from `default_for: ["cjk"]` and rely on kana/manual
   switching only?
4. Should mode order be controlled by a top-level `mode_order` array instead of
   JSON object insertion order?

## Recommended next action

For v0.4.8, do this first:

1. Add `tests/fixtures-reading-routing/`.
2. Populate it with 6-8 stable real reading examples.
3. Run fixtures without changing backend behavior.
4. Only change routing logic if the fixtures expose a clear mismatch.

This keeps v0.4.8 evidence-driven and avoids prematurely encoding a language
classifier that will be hard to trust.
